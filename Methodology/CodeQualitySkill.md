# CodeQualitySkill：VIBE Coding 代码质量守护

> **一句话定位**：AI 写出的代码在交给人类评审之前，先按团队《代码评审模板》自审一遍、自改一遍，再把模板填好一并提交。

---

## 0. 设计原则

| # | 原则 | 含义 |
|---|------|------|
| P1 | **模板驱动** | 《代码评审模板》第 1–6 章是唯一的验收标准。本 SKILL 中的每条规则都要能落到模板的某个检查项上；模板没覆盖的高危问题，统一写入"补充检查项"（第 9.3 节） |
| P2 | **左移** | 能在生成代码前用约束避免的问题，就不留到生成后自检；能自检发现的，就不留给人工评审 |
| P3 | **可量化** | 尽量给每个检查项配上阈值或可验证的信号，不写"感觉还行"这类结论 |
| P4 | **证据化** | 模板中凡填"否"或"未知"的项，"说明"栏都要写明证据（文件:行号、工具输出、坏味道 ID）；第 5 章的每一行都必须指到具体的文件和行号 |
| P5 | **小步闭环** | 一个评审单元的 Diff 建议不超过 400 行，每一步都走完"生成 → 自检 → 修复 → 填表"的闭环 |
| P6 | **如实填写** | 没有运行过的检查填"未知"，并写明原因。禁止伪造"是"，也禁止靠关闭规则、删除测试、吞掉异常来"变成是" |

## 1. 输入与输出契约

### 1.1 输入

| 输入项 | 必填 | 说明 |
|--------|------|------|
| `review_template` | 否 | 默认使用 `code_review_template.md`（附录 A 是它的条目化版本）。如果用户提供了其他模板，按第 3 节的方法重新建立映射 |
| `code_scope` | 是 | 待评审对象：文件、目录、Git Diff、PR，或本次 VIBE 会话生成的代码 |
| `context` | 否 | 需求或功能定义、设计文档、编码规范、目标语言与版本、作者和审查人 |
| `strictness` | 否 | `strict`（默认，用于生产代码）、`standard`，或 `prototype`（仅拦截 Blocker 和 Critical） |

### 1.2 输出

1. **已填写的《代码评审模板》**：章节、表格、检查项文字与模板原文**完全一致**，只填"结果"和"说明"两列；第 5 章按实际问题追加行。模板中的"样例"小节**不输出**。
2. **修复后的代码**：Blocker、Critical、Major 级问题直接修复，Minor 级给出建议。
3. **评审结论**：填入模板第 6 章，判定规则见第 7 节。

### 1.3 "结果"列取值规范

| 取值 | 含义 | "说明"列要求 |
|------|------|--------------|
| `是` | 检查项的陈述成立 | 可以为空；关键项建议写上证据，例如"pytest 42 passed" |
| `否` | 检查项的陈述不成立 | **必填**：写明问题、位置、坏味道 ID，以及对应的第 5 章行号 |
| `不适用` | 与本次代码无关，例如没有用到多线程 | **必填**：写明不适用的原因 |
| `未知` | 无法验证，例如工具无法在本地运行 | **必填**：写明原因和建议的验证方式 |
| 具体值 | 名称、数量、日期等事实类条目 | 按事实填写 |

> 注意：模板中有些条目的陈述是**否定式**，例如"不存在冗余的代码""不存在特定编译器功能"。填"是"表示**确实不存在**，填"否"表示**存在**。

## 2. 总体工作流

```
 S0 评审准备        S1 编码前          S2 编码中         S3 坏味道自检      S4 自动检查        S5 填写评审模板
(模板第0/1章) ──▶ (澄清与设计)  ──▶ (生成硬约束)  ──▶ (模板第3/4章)  ──▶ (模板第2章)   ──▶ (模板第5/6章)
                                                         ▲                                   │
                                                         └──────── S6 修复并回归 ◀────────────┘
                                                              （代码质量较好 = 否 时）
```

**退出条件**：Blocker = 0、Critical = 0；Major 要么已修复，要么写明了豁免理由。模板第 6 章"代码质量较好"填"是"。最多迭代 3 轮；第 3 轮后仍不满足时，停止自动修复，输出"重新编写并重新审查：未通过"，并列出阻塞项。

**使用场景**（对应模板第 0 章）：业务逻辑复杂、有技术难度、资源消耗大的代码，以及**所有 AI 生成的代码**，都必须完整执行本流程。人工评审建议时长为 1.5–2 小时；做好 AI 自审后，可以把人工时间集中在第 9.4 节列出的"人工关注点"上。

---

## 3. S0 评审准备：解析模板并建立检查矩阵

1. **填写模板第 1 章"关于代码"**：
   - 模块名、作者、程序设计语言、文件数：从代码和 Git 信息中提取。文件数指本次评审涉及的源文件数，测试文件单独注明。
   - 审查人员：写"AI 自审（CodeQualitySkill）"，人工审查人员再追加。
   - 版本：默认 1.0，每轮复审递增。日期：当天日期，格式 YYYY-MM-DD。
2. **加载检查矩阵**：使用附录 A，把模板的每个检查项绑定到坏味道 ID、阈值或工具规则。
3. **补全高危项**：模板没有覆盖安全、密钥、注入、测试有效性。本 SKILL 中对应的 Blocker 和 Critical 规则作为"补充检查项"输出，**不得静默丢弃**。
4. **处理冲突**：如果团队模板或项目规范与本 SKILL 的阈值冲突，以团队为准，并在"说明"中注明。

## 6. S1–S4 执行细则

### S1 编码前：澄清与设计（对应模板第 3 章）
1. 复述功能定义和验收标准，有歧义**先提问**。
2. 找到设计文档（模板第 3 章"存在设计文档"），提取模块划分和接口约定，作为生成代码的约束。
3. 阅读相邻代码，提取项目的风格准则（命名、日志、错误处理、测试框架）。
4. 搜索代码库中可复用的能力，预防 SM-V09。
5. 给出最小设计：涉及的文件、函数签名、算法选型及其复杂度、是否需要设计模式。规模超过 TH-11 时先拆分。

### S2 编码中：生成硬约束
- 只做与需求相关的修改（SM-V10），遵循项目风格（SM-V08）。
- 完整实现；暂缺的功能显式标记为 `TODO(#Issue)` 并抛出未实现异常（SM-V02，TH-13）。
- 不确定的 API 先确认（SM-V01）；新增依赖要锁定版本（SM-V18）。
- 错误处理"三问"：会失败吗？调用方如何得知失败？日志里能看到什么？
- 外部输入在边界处校验（SM-V07）；内部不变量用断言验证。
- 资源用语言提供的作用域机制管理（SM-V14）；涉及共享状态时先确定并发模型（SM-V15）。
- 同步编写单元测试，覆盖正常、边界和异常三类路径。
- 输出统一走日志框架，禁止残留 `print` 或 `System.err`（SM-V17）。

### S3 编码后：坏味道自检（对应模板第 3、4 章）
按以下顺序扫描，每个发现记录为 `{文件, 行, 问题, 坏味道 ID, 级别, 修复建议}`：
1. **Blocker**：SM-V01 / V02 / V05 / V13
2. **Critical**：SM-V03 / V04 / V06 / V07（缺失校验）/ V14 / V15 / V17（泄密）
3. **结构**：第 4 节阈值，加上 5.1–5.5 的经典坏味道
4. **逐项判定**：按附录 A 的"判定方法"，给模板第 3、4 章的每一项填写结果

### S4 自动检查（对应模板第 2 章）
按以下顺序执行（项目已有配置时优先使用项目配置，工具见附录 B）：
`编译（开启全部警告） → Lint / 静态检查 → 类型检查 → 单元测试 + 覆盖率 → 复杂度 / 重复度 → 安全与密钥扫描`
- "代码处于源代码版本控制之下"：执行 `git status` 或 `git ls-files` 验证。新文件未纳入版本控制时，填"否"并给出建议。
- "检查工具名称"填实际使用的工具，可以有多个，用逗号分隔。
- "使用检查工具检查的结果"按 `Error(n) / Warning(n)` 的格式填写，必要时附上覆盖率、复杂度等数据。
- 工具无法运行时填"未知"，**不得伪造结果**。

## 7. 严重级别与评审结论判定（对应模板第 6 章）

### 7.1 严重级别

| 级别 | 定义 | 处理要求 |
|------|------|----------|
| **Blocker** | 无法编译或运行、结果错误、安全漏洞、数据损坏 | 必须修复 |
| **Critical** | 高概率导致线上故障或隐藏故障 | 必须修复 |
| **Major** | 明显降低可维护性，或违反项目规范 | 修复；无法修复时要写明豁免理由和跟进 Issue |
| **Minor** | 局部可读性问题 | 给出建议，不阻断 |

### 7.2 模板第 6 章的填写规则

**评审结论表**

| 检查项目 | 填写规则 |
|----------|----------|
| 代码质量较好 | 同时满足以下条件填 `是`：Blocker = 0，Critical = 0，Major 全部已修复或已豁免，第 2 章编译和检查工具均无 Error。否则填 `否`，并在说明中列出未关闭问题的编号 |
| 重新编写并验证 | 首轮结论为"否"时必填：修复后编译、测试、工具检查全部通过填 `完成`，否则填 `未完成`。首轮即为"是"时填 `不适用` |
| 重新编写并重新审查 | 修复后重新执行 S3 并全部关闭的填 `通过`，否则填 `未通过`。首轮即为"是"时填 `不适用` |

> 模板规则：代码质量较好为"否"时，必须执行"重新编写并验证"和"重新编写并重新审查"。在本 SKILL 中，这对应 S6 修复循环。

**审查结果记录表**

| 检查项目 | 可选结果 |
|----------|----------|
| 审查 | `结果1：存在问题，需重新校验并重新审查`，或 `结果2：通过审查` |
| 校验 | `结果1：未通过校验`，或 `结果2：通过校验`（依据第 2 章自动检查的结果） |

### 7.3 `prototype` 模式
Major 自动降级为 Minor，Blocker 和 Critical 的规则不变：**原型代码也不能泄露密钥、不能吞异常**。

- 按 Blocker → Critical → Major 的顺序修复，每个修复只针对一个问题，不顺手重构。
- 每轮修复后重新执行 S3 和 S4，并把模板第 1 章的"版本"递增（1.0 → 1.1 → 1.2）。
